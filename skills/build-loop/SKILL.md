# 구현 루프 (Build → Verify → Commit)

## 한 단계의 흐름
1. **확인**: 이 단계의 목표와 완료 기준을 한 줄로 다시 말한다.
2. **최소 변경**: 이 단계에 필요한 것만 바꾼다. 범위 밖 리팩터링은 하지 않는다.
3. **검증**: 아래 순서로, 가능한 만큼 직접 실행한다.
   1. 문법이나 빌드 (`python -m py_compile`, `node --check`, `npm run build` 등)
   2. 테스트 (있으면 실행, 핵심 로직에는 작은 테스트를 추가)
   3. 동작 확인 (`curl -s localhost:PORT/...`, CLI 실행 결과)
   4. 화면은 사람이 확인해야 하므로, Browser 미리보기에서 확인할 PORT, 경로, 조작 방법을 나에게 알려준다.
4. **커밋**: 통과하면 `git add -A && git commit -m "<type>: <무엇을>"` (type: feat, fix, test, docs, refactor). **push는 금지.**
5. **보고**: 한 일 / 검증 (명령과 결과) / 왜 이렇게 했나 / 다음

## 디버깅 절차
1. 재현 명령을 확정하고 오류 메시지의 핵심 줄만 인용한다.
2. 원인 가설 2~3개를 세우고, 확인 비용이 싼 것부터 확인한다 (로그, print, 최소 재현).
3. 원인을 확인한 뒤 최소한으로 수정하고 다시 검증한다.
4. **같은 방식이 두 번 실패하면 멈추고**, 시도한 것과 대안 2개를 보고한다.

## 금지
- 테스트를 약하게 고치거나 결과를 하드코딩해서 통과시키기
- 요구사항을 몰래 줄이기 (줄여야 하면 명시하고 DECISIONS에 기록)
- 검증하지 않고 "완료"라고 말하기
- 서버를 중복으로 띄우기, 무거운 의존성을 몰래 추가하기

## 서버 실행
- 서버는 `0.0.0.0`에 바인딩한다. 스택별 명령과 주의사항은 `web-quickstart` 스킬을 본다.
- 오래 도는 서버는 사용자가 별도 터미널에서 실행하게 안내하거나, 직접 띄워야 하면 `nohup <cmd> > server.log 2>&1 &`로 실행하고 `tail -20 server.log`로 확인한다.

## 교차 검증
- 중요한 지점(합의문, 핵심 로직 완성, 제출 직전)에서는 **별도 터미널의 새 Codex 세션**에 리뷰를 맡길 수 있다: "변경 사항을 리뷰해줘. 요구사항 누락과 버그 위험만, 수정은 하지 마." 리뷰 결과에서 받아들인 것과 거절한 것을 이유와 함께 기록한다.
- 토큰 사용량이 추적되므로 리뷰는 중요한 지점 2~3번으로 제한한다.

## 기록
- 단계가 끝나면 `HANDOFF.md`의 STATE와 다음 할 일을 갱신한다 (`handoff` 스킬).
- 마일스톤마다 또는 요청이 있을 때 `WORKLOG.md`에 한 줄씩 추가한다 (템플릿: `{{KIT_DIR}}/templates/WORKLOG.md`).
- AI 제안을 사람이 거부하거나 수정했으면 그 사실과 이유를 남긴다.
