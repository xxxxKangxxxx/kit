# 계획 (Plan)

## 입력
- 요구사항 표 (task-intake 결과)
- **남은 시간** (모르면 나에게 묻는다)

## 범위 원칙
- **MVP** = 필수 요구사항을 입력부터 출력까지 끝까지 관통하는 가장 얇은 버전. 이것이 먼저 동작해야 한다.
- 우선순위: 필수 > 담당자가 강조한 것 > 시연했을 때 가치가 큰 것 > 선택
- 버릴 것을 명시한다. 버린 이유는 DECISIONS에 남긴다.

## 기술 선택 원칙
- 과제가 지정한 스택이 있으면 그것을 쓴다.
- 지정이 없으면 **환경에 이미 있는 것**을 먼저 쓴다: `node -v; python3 --version; pip list 2>/dev/null | head -30`
- 의존성은 최소로 한다 (설치 시간, RAM 제한 때문). 익숙하지 않은 프레임워크는 피한다.
- 웹이면 `web-quickstart` 스킬의 스택별 주의사항을 확인한다.

## 시간 배분
- 구현에 쓸 시간 ≈ 남은 시간 × 0.6, 검증·버그 수정 ≈ 0.2, 문서·제출 ≈ 0.2
- 한 단계는 25분을 넘지 않게 쪼갠다.
- 단계마다 **실행 가능한 완료 기준**을 적는다 (예: `curl /api/x`가 200과 JSON을 반환, `pytest` 통과).
- 표시할 지점: 중간 점검 (전체의 약 50%), 기능 동결 (종료 40분 전), 제출 시작 (종료 10분 전)

## 산출물
- `PLAN.md` (템플릿: `{{KIT_DIR}}/templates/PLAN.md`, 과제가 정한 형식이 있으면 그것)
- `DECISIONS.md`에 핵심 결정 2~4개: 스택, 데이터 구조, 범위에서 뺀 것
- 응답: 계획 요약 5줄 이내 + **"이대로 진행할까요?"**. 승인 전에는 구현하지 않는다.

## 중간 점검 (재계획)
1. PLAN 대비 진행 상황 표 (완료 / 진행 중 / 미착수)
2. 남은 시간으로 끝낼 수 있는 것과 없는 것
3. 뺄 목록과 각 항목을 뺐을 때의 영향
4. 승인을 받으면 PLAN.md와 DECISIONS.md를 갱신한다.
