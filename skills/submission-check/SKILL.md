# 제출 전 점검

## 1. 제출물
- 과제가 요구한 파일이 모두 있는지 **경로와 함께** 표로 보여준다 (있음 / 없음 / 비어 있음).
- 남은 placeholder 찾기:
  `rg -n "TODO|TBD|FIXME|\(결정 제목\)|\(결과물 이름\)|^\| *\| *\|" --glob '*.md'`
- 비밀정보 찾기: `rg -n -i "api[_-]?key|secret|token|password" --glob '!**/node_modules/**'` (값은 출력하지 않는다)
- 불필요한 대용량 파일: `du -sh * .[^.]* 2>/dev/null | sort -h | tail -10`. `node_modules`, `.venv` 등은 `.gitignore`에 넣는다.

## 2. 실행 재현
- README(또는 VERIFICATION)에 적힌 실행 방법을 **적힌 그대로** 다시 실행해 본다.
- 실패하면 문서나 코드를 고친다. 시간이 없으면 문서에 한계로 적는다.

## 3. 문서와 구현의 일치
- README의 기능 목록과 실제 구현을 비교한다. 없는 기능을 있다고 쓰지 않는다.
- VERIFICATION의 결과가 **최신 실행 결과**인지 확인한다. 아니면 `미검증`으로 바꾼다.
- DECISIONS의 내용이 최종 구현과 맞는지 확인한다 (중간에 바뀐 결정 반영).
- 채점 에이전트는 **문서와 실제 코드·커밋이 연결되는지** 대조한다. 문서의 주요 주장마다 해당 파일이나 커밋이 있는지 확인한다.
- `HANDOFF.md`를 최종 상태로 갱신한다.

## 4. git
- `git status`가 깨끗한지 확인하고 마지막 커밋을 만든다 (`docs: finalize submission`). push는 금지.

## 5. 후속 서술형 대비 브리핑 (파일로 저장하지 않고 답으로만)
서술형은 AI 없이 직접 답한다. 내가 **내 말로 설명할 수 있게** 쉬운 말로 정리한다.
1. 핵심 결정 5개: 무엇을 / 왜 / 대신 포기한 것
2. 리뷰어가 물을 만한 약점 3개. 각각 **약점(구체적인 코드 위치) → 왜 위험한가(파급) → 다음에 무엇을 검증하고 어떻게 고칠까** 3단계로
3. 숫자: 구현한 기능 수, 테스트 수와 결과, 처리하는 데이터 규모, 합의한 성공 기준의 달성 여부
4. 구조 설명: 요청 하나가 들어와 결과가 나올 때까지 거치는 파일과 함수 흐름 (3~5단계)
5. AI 결과를 사람이 바로잡은 지점 2개
6. 장애 시나리오 2개: 무엇이 잘못되면 어떻게 드러나고 어떻게 대응하나

마지막으로 나에게 알린다: "에디터 저장 상태가 '저장됨'인지 확인하고, 상단 '제출하고 문제풀기'로 진행하세요."
