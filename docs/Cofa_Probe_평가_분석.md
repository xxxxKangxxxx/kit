> 조사일: 2026-10-29. 근거는 언론 보도(크래프톤 발표 기반)와 코파톤 참가 후기 1편이 중심입니다.
> **SK하이닉스 2차 예선의 채점 기준은 공식적으로 공개되지 않았습니다.** 아래는 같은 플랫폼이 쓰인 코파톤(2026-07-30)의 사례에서 추론한 것입니다. 이후 플랫폼이 바뀌었을 수 있습니다.

## 2. 무엇을 평가하나

### 2-1. 공식 발표 (크래프톤)
- 평가 축: **기술 관리(Technique) · 의도 관리(Intent) · 인지 관리(Cognition)**
- 보는 과정: 문제 정의 → AI 역할 배분과 지시 → 근거 탐색 → 의사결정 → 오류 수정 → 결과 검증
- 세부 기준:
  - 코드의 **실행성, 구조, 보안**
  - "AI에 **목표와 제약을 정확하게 전달**했는지"
  - "AI가 만든 결과를 **직접 검증하고 수정**했는지"
  - "결과의 **작동 원리와 실패 가능성을 설명**할 수 있는지"
- "같은 결과물을 만들더라도 AI에 어떤 역할과 맥락을 부여했는지, **잘못된 답을 어떻게 발견하고 접근법을 수정했는지**에 따라 평가가 달라질 수 있다." (데일리안)
- 제품 인터뷰: "한 사람이 과제를 푸는 과정을 **20개가 넘는 에이전트**가 지켜보며 세 가지를 봅니다. **결과물의 완성도, AI를 이끈 방식, 자기가 만든 것을 설명할 수 있는지**예요."
- 요구사항은 "요청은 몇 줄뿐이고, 무엇을 만들어야 하는지는 **가상의 현업 담당자에게 직접 물어서** 알아내야" 하는 구조입니다.
- 채점 구조: 기준 적용과 점수 환산은 **코드**가, 맥락을 읽는 정성 판단은 **LLM 평가 에이전트**가 맡습니다. Codex로 만든 "메타 하네스"로 같은 제출물을 여러 번 채점해 재현성을 검증합니다.
- 박재민 AI Frontier 본부장: "AI와 함께 **문제를 정의**하고 **근거를 확인**하며 결과를 **끝까지 검증**하는 데서 나온다"

### 2-2. 코파톤 참가자(FDE Top 6)가 본 실제 채점 화면 (브런치 후기)
| 축 | 세부 항목 | 후기 관찰 |
|---|---|---|
| **기술 (Technique)** 100점 | 코드 유지보수성, 요구사항 충족도, 기능적 정확성, 실무적 품질 위험, 제출물 완성도 | "AI가 만든 산출물을 본인이 직접 장악해서, 실제로 돌아가게" |
| **의도 (Intent)** 100점 | Output 목표 구체화, 재사용 가능한 작업 체계, 의도 갱신과 맥락 유지, **검증 루프 설계**, 문제 상황과 제약 정의, **작업 분해·위임 설계** | **"가장 변별력이 컸던 축"** |
| **인지 (Cognition)** 100점 | AI 산출물의 동작과 리스크 예측, 구조 이해, **의사결정 근거 이해** | **"참가자 전원이 가장 낮았던 축"** |
| 소통 (Communication) | 다른 사람이나 다른 세션이 이어받을 수 있는가 | FDE 트랙 전용. **handoff 스킬과 문서를 만든 Top 3가 높게 평가됨** |

- AI 심사자가 **코드, 커밋, 대화 로그를 직접 읽고**, 항목마다 충족이나 부분충족 판정과 **증거 위치**를 남깁니다. **문서와 실제 코드·커밋이 연결되는지 대조**합니다.
- "과정 전체(채팅 로그·터미널·git log·테스트 결과)가 채점 표면"

### 2-3. 확인 문제 (제출 후, AI 없이)
- 제출물을 보고 즉석에서 생성됩니다. 예: "특정 부분을 왜 그렇게 만들었나", "장애가 나면 어떻게 대응하나"
- **시스템이 문항마다 모범 답안을 미리 만들어 두고**, 모범 답안은 항상 3단계입니다.
  1. **내 코드의 구체적 약점을 짚는다**
  2. **그것이 왜 위험한지 파급을 설명한다**
  3. **다음에 무엇을 검증하고 개선할지 계획을 낸다**
- 후기 작성자: "조리 있게 설명하기가 참 어렵더군요". 답변에 문제가 있어 발표 직전 **재심문 2문항**을 받기도 했습니다.
- SK하이닉스 2차 예선은 **6문항 × 5분**으로 코파톤(5 × 3분)보다 길어서, 3단계 구조를 다 쓸 시간이 있습니다.

## 3. 좋은 평가를 받은 행동 (후기 기준)

### 문제 발굴과 합의
- 실무자 AI와 인터뷰하며 `INTERVIEW.md`를 남겼습니다.
- 처음에는 "자동화, AI" 같은 **해법 단어를 쓰지 않고** 다음 순서로 캐물었습니다: **에피소드 → 현재 우회 방법 → 정량화 → 당사자 → 경계**
- **서면 합의문**: 문제, 병목, **성공 기준(숫자, 현재값, 측정 방법)**, 만들 것과 안 만들 것, 제약을 정리해 **실무자에게 확인받고**, 이를 지침 파일의 "합의된 성공 기준"에 기록했습니다. 구현 착수 전 필수 관문으로 두었습니다.
- 주의: 코파톤에서는 **README에 문제와 해법이 이미 자세히 적혀 있었습니다.** 그래도 담당자와의 확인과 성공 기준 합의를 거치는 것이 차별점이 됩니다.

### 설계 원칙
- **판정과 계산은 고정 코드로, AI(LLM)는 해석과 초안만** 맡깁니다. (평가 측 메타 하네스도 같은 원칙을 씁니다.)
- 간극 하나를 깊게 팝니다.
- "세 가지 왜": 진짜 데이터 원천, 안 풀면 드는 비용, 내가 떠난 뒤 유지할 사람

### 진행 관리
- 진행 단계 `STATE`(발굴 → 서면 합의 → 뼈대 → E2E v0 → 중간 검증 → 수용 확인 → 제출)를 **커밋마다 갱신**했습니다.
- 단계가 바뀔 때마다 계획에서 벗어났는지, 증거 없이 체크한 항목이 있는지, 너무 순조롭지 않은지 스스로 감사했습니다.
- 메인 세션과 별도로 **감시·리뷰용 세션**을 두고, 중요한 산출물(합의문, 제출 직전 코드)은 **교차 검증**했습니다.

### 아쉬웠던 점 (후기)
- 메인 세션에서 컨텍스트 압축(compact)이 반복되었습니다. **handoff를 남기고 새 세션으로 넘어갈 시점**을 미리 정하지 않았습니다.
- 어떤 도메인에도 80%는 쓸 수 있는 범용 키트와 참고할 오픈소스 후보 목록을 미리 준비하지 않았습니다.
- 풀타임 리허설을 계획대로 하지 못했습니다.
- "하네스를 최대한 걷어내는 게 오히려 높은 퍼포먼스를 보여주기도" 했습니다. 과한 장치는 방해가 될 수 있습니다.

### 다른 대회 수상자 (크래프톤 AI R&D 해커톤, 참고)
- "끝까지 **제출 가능한 결과물**을 만들고, 여러 접근 중 **가장 방어 가능한 답**을 골라낸 점"
- 제출 시각을 정해 두고, 미완성이어도 그 시각에는 제출 준비에 들어갔습니다.
- AI가 샘플 정답에 과하게 맞추려는 것(과적합)을 발견하고 되돌렸습니다.
- "AI를 잘 쓰는 것과 AI에 끌려가는 건 다르다"

## 4. 이번 시험에 적용할 전략

| 평가 포인트 | 할 일 | 킷 반영 |
|---|---|---|
| 문제 정의 (Intent) | README에 해법이 있어도 **담당자 인터뷰 → 합의문(성공 기준 숫자 포함) → 확인받기** | `task-intake`, `STAKEHOLDER_QA.md` 합의문 섹션 |
| 작업 분해와 위임 (Intent) | PLAN의 단계별 완료 기준, 한 번에 한 단계씩 위임 | `task-plan`, `build-loop` |
| 검증 루프 (Intent) | 단계마다 실행 검증과 커밋. 중요 지점은 별도 세션 리뷰 | `build-loop`, `prompts.md` 리뷰 프롬프트 |
| 의도 갱신과 맥락 유지 (Intent) | 범위가 바뀌면 PLAN과 DECISIONS 갱신. `STATE` 한 줄 유지 | `HANDOFF.md`의 STATE |
| 결과를 직접 장악 (Technique) | 요구사항 충족 표, 테스트, 보안 점검, 실행 재현 | `submission-check`, `VERIFICATION.md` |
| 결정론적 설계 (Technique) | 계산과 판정은 코드로, LLM은 해석과 초안만 | `AGENTS.md`, `task-plan` |
| **인지 (가장 낮았던 축)** | AI가 만든 구조를 **내가 설명할 수 있게** 단계마다 "왜"를 확인. 약점과 리스크를 스스로 정리 | `submission-check` 브리핑 |
| 이어받기 (소통) | `HANDOFF.md`(상태, 다음 할 일, 주의점)로 새 세션이 이어받을 수 있게 | `handoff` 스킬 |
| 문서와 코드의 연결 | 문서에 적은 결정이 실제 커밋과 코드에 있는지 대조 | `submission-check` 3번 |
| 확인 문제 | **약점 → 위험과 파급 → 다음 검증·개선 계획** 3단계로 답하기 | 플레이북 F절 |

### 하지 말 것
- 검증 없이 AI 결과를 그대로 받아들이기 (평가 문구: "잘못된 답을 어떻게 발견하고 접근법을 수정했는지")
- 문서에는 있는데 코드에는 없는 기능 (문서와 코드를 대조하는 채점 방식)
- 같은 요청을 반복하는 비효율 (SK하이닉스는 토큰 사용량을 추적한다고 명시)
- 하네스와 문서를 과하게 만들기: 기록은 짧게, 결과물에 시간 쓰기
